# Phase 3: explore historical Olist forecasts

Select **Olist historical forecasts** in the existing Streamlit workspace. This
page is separate from the fictional USD demo. It displays only **2016–2018 public
historical Olist merchandise value in BRL**. It makes no AI requests, needs no
OpenAI key, trains no model, and does not forecast current company operations.

## Prepare the local derived files

Start PowerShell in your local repository checkout after installing the project
requirements. Before this PR is merged, use branch `feat/olist-historical-dashboard`;
after merging, use the updated `main`. Download the four source CSVs manually as
described in [the ingestion guide](olist.md), respecting the publisher's license,
and place them in `data\olist\raw`. Nothing licensed is bundled with this page.

```powershell
& .\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-forecast.txt
& .\.venv\Scripts\python.exe -m olist --source .\data\olist\raw --output .\data\olist\processed
& .\.venv\Scripts\python.exe -m olist.forecast --input .\data\olist\processed\weekly_revenue.csv --quality .\data\olist\processed\quality_report.json --output .\data\olist\processed\forecast_results.json
& .\.venv\Scripts\python.exe -m streamlit run streamlit_app.py
```

The page requires all three local derived files:

- `weekly_revenue.csv`: recorded weekly integer-cent revenue and partial flags.
- `quality_report.json`: definitions, reconciliation inputs and coverage evidence.
- `forecast_results.json`: Phase 2 **schema version 2**, historical predictions,
  errors, provenance and forecast-availability safeguards.

All stay under ignored `data/olist/`. No new dataset, dependency, API key, `.env`,
model fitting or agent integration is required to *view* a prepared report. NumPy
is needed to reuse Phase 2's validation and coverage checks; those imports are
lazy and isolated from the original workspaces. The original demo still works if
the Olist files or optional forecasting setup are unavailable.

## A short walkthrough

1. Read the historical observation and evaluation dates. Recorded-week count
   includes partial boundaries; backtest-week count is the scoring window.
2. Check the next-week illustration's status. **Unavailable means no prediction**:
   no number, replacement zero, alternative model or chart point is shown. Reasons
   explain partial-target overlap and suspicious recent coverage. Available values
   are labeled historical illustrations, never actuals or operational guidance.
3. Compare MAE (BRL), WAPE (%) and signed bias for all three methods. Lower error
   is better. WAPE is not an accuracy percentage; undefined WAPE remains unavailable
   when the evaluated actuals are all zero. The page explicitly says whether ridge
   wins, ties or loses against the best simple baseline. Ranking uses the original
   report's absolute-error rule and deterministic tie preference.
4. Hover and zoom on the recorded-versus-predicted chart. Predictions are plotted
   at their **target week**, not the last training week. Faded actuals show initial
   training, solid lines show recorded values, dashed lines show rolling backtest
   predictions, and squares show excluded partial actuals. The next-week illustration
   is separate and never appended to the historical chart.
5. Filter chart dates, choose backtest methods or hide initial training. These
   controls change only the chart and optional evidence table. Global score cards,
   ranking, coverage warnings and availability safeguards never change with filters.
   Clearing methods shows actuals only. A date range containing no matching weeks
   shows an empty state.
6. Read reconciliation and coverage warnings. **Inspect quality and provenance**
   shows partial/zero/outlier dates, recent order evidence, source hashes and the
   fixed endpoint-sensitivity comparison. This diagnostic is not the primary score
   or winner. The page keeps all zeros and warns that calendar completeness does
   not establish source completeness.

Business interpretation is deterministic, derived from the saved comparison and
definitions. It does not claim causes, profit, verified zero demand or present-day
performance. A simpler baseline beating ridge is an honest result; no method is
promoted simply for being machine learning. See [forecasting methodology](forecasting.md)
for the fixed evaluation window, coverage heuristics and limitations.

## Missing, outdated or inconsistent reports

The page shows setup instructions instead of charts if files are missing, corrupt,
use an older schema, disagree, or were generated by different forecasting code.
It never substitutes fictional sales or default zeros. Regenerate ingestion and
forecasting together, then rerun/refresh the app.

The loader checks input and producer-code SHA-256 hashes, BRL definitions, source
timeframe, integer-cent reconciliation, target/training dates, actual values,
prediction ranges, recomputed errors/ranking, coverage and endpoint sensitivity.
It independently reapplies the Phase 2 availability rules. A report that re-enables
a suppressed point prediction or embeds a number in an unavailable field is rejected.
Files changed during loading are rejected; content bytes drive the bounded cache,
so replacing a file does not leave stale charts behind. An old producer-code hash
requires regeneration even if the report still looks structurally valid.

These are consistency checks, not cryptographic authentication of the report or
independent verification of model predictions. The UI never reruns ridge; it checks
the saved results. Source coverage remains unverified, and historical delivered
statuses may not have been known at the original reporting time.

## Tests and limits

```powershell
& .\.venv\Scripts\python.exe -m pytest -q
& .\.venv\Scripts\python.exe -m pip check
```

Tests generate tiny fictional derived files in temporary directories. They cover
alignment, BRL conversion, ranking, filters, key-free access, suppression, invalid
or absent files, cache refresh, dependency gating and the existing demo/Live Mode
regressions. Runtime QA also uses a fictional fixture because the real licensed
files are unavailable in the development checkout. No new real-data accuracy
claim is made by this dashboard phase. Browser visual polish and real-data coverage
still need review on your local files; a healthy runtime does not certify completeness.

Phase 3 verification: **211 tests passed**, including 29 dashboard cases. Dependency
checks and type checks on the edited app modules passed. Headless running-app QA
confirmed the missing-data fallback, target-aligned chart filters, quality evidence
and partial-target suppression using fictional derived files; no new server warnings
were observed. The temporary QA servers were stopped afterwards.
